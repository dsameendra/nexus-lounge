# Nexus Lounge

Virtual watch-party PWA: rooms with LiveKit voice/chat/screen share, synced YouTube playback, Twitch and Kick, queue, roles, TV mode. General purpose (League of Legends Worlds is only a one-line mention in the README).

## Layout
- `apps/web`: Next.js 16 (App Router), React 19, Tailwind 4, Auth.js v5 (Discord + guest credentials).
- `apps/server`: Fastify 5 + `ws`. Rooms live in memory; WebSocket protocol validated with zod.
- `packages/shared`: types, `protocol.ts`, sync maths, URL parsing, PTT, volume curve, sound cues.

## Commands
- `pnpm install`, `pnpm dev` (web 3000, server 4000), `pnpm typecheck`, `pnpm build`
- `pnpm --filter @nexus/shared test`, `pnpm --filter @nexus/server test`
- `pnpm livekit` runs LiveKit locally (Docker; stop it when not needed).

## Conventions
- TypeScript strict. Node runs `.ts` directly, so imports use the `.ts` extension and only erasable syntax is allowed (no enums, no parameter properties).
- Validate every WebSocket message with the zod schemas in `packages/shared/src/protocol.ts`. Enforce permissions on the server and in the LiveKit grant, never only in the UI.
- Match surrounding code: few comments, small components, Apple-style UI (restrained, rounded, blur, system font).
- Sheets and popovers render through portals (popovers into the fullscreen element when active).

## Layout variants
- `pl:` = phone landscape (short, landscape, under 1024px wide). `compact:` = phone portrait or phone landscape. Defined in `globals.css`; use them instead of `max-sm:`/`landscape:` so the two phone orientations stay in sync.
- Use container queries (`@container`, `@md:`) inside the player controls: the stage can be narrow because of the side panel, not because of the viewport.
- Use `overflow-clip`, not `overflow-hidden`, on layout shells: hidden containers can be scrolled by focus and shift the whole app sideways on iOS.
- Fullscreen boxes set `--safe-l/--safe-r` (notch insets); the player and share area offset themselves with them so the picture stays centred in the visible area. Fit/Fill (`useVideoFit`) scales the YouTube host with container query units (`cqw/cqh`) rather than `object-fit`, because the iframe is cross-origin.
- Menus use `Popover` (portal, fixed); never position dropdowns inside cards.

## Gotchas
- **Kick** (`type: "kick"`, channels only, always `isLive`, `kick:live:<slug>`): `player.kick.com/<channel>?autoplay=&muted=` in an iframe (`lib/players/kick.ts`; the embed has no API and no framing headers). Like Twitch live it has no shared clock (`isUnsyncedSource` in `types.ts`, used by the server and `StreamPlayer`), never gets an overlay (`isEmbedOnlySource`), and is torn down on every switch (hidden, it would keep playing sound). Mute can only be passed in the address, so muting reloads the embed. Kick videos and clips are refused in `parseMediaUrl`.
- **Never overlay a Twitch embed.** Twitch pauses playback if anything covers it. Tear down and recreate the Twitch player on every stream switch.
- YouTube embeds cannot be told a quality (the write APIs are no-ops); the player's pixel size drives what YouTube serves. Reads work. Captions use an undocumented module, so guard every call (`safe()`).
- Per-stream clock: `{position, playing, updatedAt}`; correct drift with playback rate first, seek rarely and debounced.
- Screen share stream ids are `screen:<identity>`.
- iPhone has no Fullscreen API for elements: `useStageFullscreen` falls back to an immersive CSS mode. Decide at creation time, never rebuild a YouTube iframe (iOS blocks autoplay on a new one): on devices without the API, viewers who cannot control the stream get YouTube's own controls (`fs=1`, whose fullscreen button opens the native iOS player); controllers keep our synced controls. Twitch always shows its own controls. Screen shares call `video.webkitEnterFullscreen()`. Cross-origin iframes can't be sent to native fullscreen programmatically.
- Twitch needs 400x300: smaller stages scale the whole embed down (`TwitchAdapter` ResizeObserver) instead of cropping its controls.
- Join state: everyone joins muted and deafened; `LiveKitRoom audio={false}` so the mic is only requested on unmute.
- Queue: `room.queue` is explicit (`queue.*` messages); with an empty queue `queue.advance` falls back to library order. Playlists are YouTube only, scraped server-side from the playlist page (`playlists.ts`, no API key), items are sent on demand with `playlist.open`.
- TV output: `TvRoom` has a fullscreen toggle (top right, shows on mouse or key activity or focus, hidden over Twitch which has its own; `F` too) because Start watching enters fullscreen by itself and the viewer may want out. The TV is a guest member whose ticket carries `tvOf` (the owner id). `useTvOutput` (per-room localStorage choice: here/tv/both) drives `Stage`, `StreamPlayer` and `VoiceAudio`; "tv only" sets the local player `visible=false`, "both" mutes this device until the user turns sound on. With no TV connected the mode falls back to "here".
- Player bar: below `@md` Quality, Fit/Fill and AirPlay collapse into `MoreMenu`; Subtitles always stay on the bar.
- Accounts: no database. Profile edits (name, preset avatar from `public/avatars`) are stored in the Auth.js JWT via `unstable_update({ profile })` and applied in the `session` callback. `/account` can delete the account: the web route calls server `POST /account/delete`, which refuses (409 `in_room`) while the user is connected to any room and otherwise forgets them (`rooms.forgetUser`), then the session is cleared. Public pages `/terms` and `/privacy` back the links Discord requires; update their dates when behaviour changes.
- Admin (`/admin`): live read-only overview of rooms and people. Needs `ADMIN_SECRET`, `ADMIN_DISCORD_IDS` (web + server) and `ADMIN_TOTP_SECRET` (web); with any missing it is off and the server route is not registered. Layers: allowlisted Discord session (guests never) + TOTP code (single use per step, 5 tries per 5 min) -> 30 min `__Host-admin` cookie -> the web app mints a 60 s single-use token (`aud: admin`, own verifier in `packages/shared/src/admin-token.ts`) for the server's `GET /admin/overview`. Every failure is the stock 404. The overview is built field by field in `rooms.adminOverview` (never spread room/member objects; names stripped of invisible characters). Keep `/admin` and `/api/admin` out of the service worker and cache. Actions (close a room, remove a person): the request token carries a structured `act` bound to one operation; members are addressed by an opaque HMAC `ref` (no IDs leave the server); the web route additionally needs same-origin `Sec-Fetch-Site`, `Origin` equal to `AUTH_URL`, a CSRF header derived from the admin cookie, JSON content type, and an admin cookie issued in the last 5 minutes (else it asks for a fresh code). The host can't be removed (close the room instead). Removing someone also drops TVs they paired; LiveKit leftovers are cleaned by `reconcileVoice` every 30 s.
- Local video files: a stream with `source.type = "local"`, id `local:<32 hex fingerprint>` (`packages/shared/src/local-file.ts`: SHA-256 of the size plus the start, middle and end megabyte), `Stream.file` = name/size/duration. The file never reaches the server. Never queueable, never live, autoplay skips them. Only the owner may establish the first position. Adding needs the room's `sharing` rule (same as screen share), 5 per person max. Two ways to watch, chosen per viewer: play your own copy (`LocalEntry` in `lib/local-entry.ts`, one per file in a module-level `registry` so it survives voice reconnects; verified by fingerprint, wrong files refused) or watch the owner's live feed. `LocalFilesProvider` (inside `LiveKitRoom`, in both the room and the TV) runs the sync loop for every open file, restores remembered files (IndexedDB handles, Chromium only), publishes the feed on demand and subscribes to it only while this device watches it. `LocalPlayer` is the UI (Stage and TvRoom render it for local streams; `StreamPlayer` ignores them). Members carry `feed` (the local stream they receive through the feed) so the owner publishes only while someone needs it, and stops 10 s after the last viewer. The feed travels as `Track.Source.Unknown` tracks named `file:v:<streamId>` / `file:a:<streamId>`: `livekit-server-sdk` cannot put that source in a token, so `allowFeedSource` (`livekit.ts`) re-signs it; `updateParticipant` accepts it; removing the stream or `share.stop` revokes it (`canFeed`). Viewers only accept tracks from `stream.addedBy.id`. Keep the owner's `<video>` at full volume, unmuted: a Web Audio source follows the element's volume, so all local volume/mute goes through the speaker gain node (deafen is for voice chat only and does not silence the film) and never touches the feed. Video capture is `captureStream()` where it exists, otherwise a canvas + `requestVideoFrameCallback` (Safari). Files keep playing while parked off screen (`parking()` in `LocalPlayer.tsx`) because the feed depends on it. Suite `13-local-file.mjs` needs LiveKit and ffmpeg.
- Stremio, magnets and links (`torrent` and `link` source types, same device-stream machinery as local files): host and controllers only. `torrent` id is `<infoHash>-<fileIdx>` and the room carries sanitised trackers (`sanitizeTrackers`: public hosts only, so nobody can aim another person's Stremio at their LAN); `link` id is random and the URL is NEVER sent to the server or room (it lives in the owner's tab and `sessionStorage`; `Stream.file.size` may be 0 for links that don't report one). Friends verify their own copy with `sameMedia` (size + length) or the torrent's size. `lib/stremio.ts` talks to the Stremio streaming server (`/settings`, `POST /{hash}/create`, `GET /{hash}/{idx}` with ranges, `/{hash}/{idx}/stats.json`, `/hlsv2/probe?mediaURL=`, `/hlsv2/{id}/master.m3u8?mediaURL=&videoCodecs=&audioCodecs=`; unofficial, so keep it in this one file). A page on https reaches `127.0.0.1` only with Chrome's local-network permission (asked once when `checkStremio` runs; requests carry `targetAddressSpace: "loopback"` with a retry without it) and Safari blocks fetches to it (mixed content) but still loads `<video>` from it, so friends there play blind: HLS without checks. Link plan (`planLink`, `resolveLink` in `lib/remote-media.ts`): direct in the browser when the final address is https and CORS allows reading it, else through Stremio's HLS (`hls.js`, native HLS only on Safari); `LocalEntry` sets `crossOrigin="anonymous"` for URL sources because Web Audio and the live feed need CORS media. Suite `14-stremio.mjs` uses a mock Stremio and mock link hosts (`e2e/stremio-mock.mjs`); `STREMIO_REAL=1` also runs a real magnet and a real HEVC conversion through the Stremio app on this computer.
- Playback speed (device streams): `directPlayable` (`lib/codecs.ts`) asks the decoder (`MediaSource.isTypeSupported`, `canPlayType`), not the user agent: Matroska plays as it is where the browser has a demuxer (Chrome, Edge), HEVC/AC3/E-AC3 are copied where the machine decodes them, everything else goes through Stremio's HLS. `urlSource` (`remote-media.ts`) queues `fallbacks` (direct, a playlist copying what the browser decodes, then plain H.264/AAC) and `LocalEntry.fallBack` moves on when the element errors, has no picture, or hls.js fails fatally; `opened()` replaces the old ready wait. hls.js waits per `PATIENT` in `local-entry.ts` for the converter's first byte (the default re-asked and restarted ffmpeg); `hlsRetries` is one shared budget for the entry, reset when playback succeeds. A direct file that is slow to open also falls back (direct files only, so it never skips ahead of a slow converter), starts at the room's position (`startAt`) and is kept out of subtitle tracks (`enableWebVTT: false`; otherwise Stremio's own track showed on top of ours). `LocalEntry.perf` logs open time, first picture and stalls (`console.debug [nexus stream …]`, only when `localStorage` `nexus-debug` is `1`); `streamHint` shows a reason in `DeviceFooter` only after repeated stalls (Stremio's download limit from `/settings`, no peers, slow swarm, CPU conversion). The probe has no profile or bit depth, so a 10-bit file that claims H.264 is caught by the fallback, not by the check. One person can add 5 device streams: e2e that adds more needs a second owner.
- Live YouTube streams (`StreamPlayer`): no continuous sync at all. Every viewer's live edge differs by seconds and a player can only play what it buffered, so chasing the room's position made everyone seek and stutter forever. The room's position is a hint used once per stream, on a controller action and on join/load (`m.immediate`): a viewer within `LIVE_EDGE_TOLERANCE` of the edge jumps to their own edge (`liveJumpTarget`), anyone else goes to the position asked for, and only if more than `LIVE_SEEK_THRESHOLD` away. Speed is never changed; play/pause stays shared. Go live (controllers) sends the edge minus `LIVE_EDGE_MARGIN`; for everyone who can't control, the button jumps them to their own edge (`liveEdgeTarget`) whatever the room position is; Resync stays room-based.
- Subtitles (personal, never sent to the room): only on an open `LocalEntry`, so people watching the live feed have none (the feed is picture and sound). Sources are `SubtitleOption`s (`lib/subtitles.ts`): tracks inside the video (read from the SUBTITLES entries of the HLS master Stremio builds, segments joined with `mergeVtt`; needs the owner's Stremio reachable, so not Safari's blind mode), subtitle files that came with the torrent (through Stremio's `/subtitles.vtt?from=`, which fixes encodings), a `.srt`/`.vtt` picked from the computer, and Find subtitles online (`SubtitleSearchSheet`: Cinemeta title search then the OpenSubtitles add-on by IMDb id, CORS open, files must be https; a file hash alone finds nothing). `LocalEntry` adds each as a `<track>` from a blob and shows one; the browser draws it (`video::cue` and `data-sub-size` in `globals.css`). The language choice (`nexus-subtitles`: code or `off`) and size live in localStorage and auto-pick a track in the browser's language. Stremio's HLS subtitle segments can drop the first cues of a track (Stremio's output, not ours). Embedded tracks of a file on disk can't be read by a browser.
- `useWakeLock` keeps the screen on in rooms and TV mode (Screen Wake Lock API, re-acquired on visibility change).
- Production sits behind Cloudflare (proxied, SSL Full). Rate limits use `clientIp(request)` (`apps/server/src/client-ip.ts`), which trusts `CF-Connecting-IP` only from Cloudflare's ranges; the Railway addresses still work directly with `TRUST_PROXY_HOPS=2`. `www` and the old Railway web address redirect to the apex in `next.config.ts`; HSTS (6 months, no preload) is sent from there too. See `docs/railway-deploy.md`.
- `NEXT_PUBLIC_*` values are baked at build time; `SERVER_WS_URL` is the runtime override.
- iCloud can create `* 2.ts` duplicates inside `.next`; tsconfig excludes them.
- Rooms vanish on server restart; keep a single server instance.

## Secrets and deploy
- Never commit `.env`, `.env.railway` or `.tmp-*` (all ignored). `.env.example` is the only env file in git.
- `main` is protected (applies to admins too): changes go through a branch and a pull request, the `check` CI job must pass, no force-pushes or deletion. Squash-merge with `gh pr merge --squash --delete-branch`.
- Railway services `server` and `web` are connected to GitHub and deploy on every push to `main`. Config templates and steps: `docs/railway-deploy.md`, `docs/railway/`.

## Tests
`pnpm --filter @nexus/shared test`, `pnpm --filter @nexus/server test`, and the browser suites in `e2e/` (`cd e2e && node run.mjs`; see its README). Add an e2e check for UI behaviour, and assert geometry (rects, `elementFromPoint`) rather than eyeballing screenshots.

## Manual testing
Run server and web with a LiveKit instance and Discord keys, or use guest login. Use two browser windows in one room. `AUTH_SECRET` must match between web and server.
